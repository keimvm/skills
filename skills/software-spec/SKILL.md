# 企画書から、実装に必要な最小限を決める

企画書を出発点に、実装を始める前に決めておくべきことを、ユーザーと一つずつ決める。論点ごとに何を決めるのか、なぜ今なのかを短く説明し、提案と推奨理由を示す。決まったことを `software-requirements.md` と `software-stack.md` に残し、細部は実装時に委ねる。

## 入口

- 標準の入力は `project-plan` が作る `requirements.md`。別名の企画書も、ファイル名や場所を変えずにそのまま使える。
- 指定がなければ既存の文書配置や `docs/requirements.md` を探し、見つからない、または迷うときだけ、どの企画書を使うか尋ねる。
- 企画書を読み、目的・実現したい状態・範囲・制約を短く言い換えて認識を合わせる。未確認・推定・未決は、その状態のまま引き継ぐ。
- 既に決まっていることは問い直さない。実装の方向を左右する未決事項から、今扱う論点を一つ選ぶ。

## 今決めること、決めないこと

今決めるのは、決めないと実装の方向が分かれること、後から変えると影響が大きいこと。必要な機能と主要な振る舞い、何ができれば完成か、実現に必要な技術構成がこれにあたる。

- 文書の項目を埋めるためだけの決定は増やさない。将来あるかもしれない要望を理由に、機能・依存関係・構成を足さない。
- ファイル構成、内部の関数や型、細かな画面配置は、要件や制約に関わらない限り実装時に委ねる。技術の種類やバージョンも、今選ぶ必要があるものだけ扱う。
- 「未決」と「実装時に委ねること」を分ける。未決はまだ判断が必要な論点、委ねることは合意した要件・制約の範囲で実装者が決めてよいこと。実装の方向を左右する未決を、細部として片付けない。

## 一つの論点の進め方

一回の返答で一つの論点を、この流れで扱う。毎回同じ見出しを並べる必要はない。

1. 今回決めることと、今決める理由
2. 選択肢と、それぞれを選んだときの違い。比較が要るときだけ、有力な二、三案
3. 推奨と、その理由。どの要望や制約に合うのか、何を諦めるのか
4. ユーザーの考えを聞く、一つの問い。推奨への賛否だけを求めず、別の考えや疑問も話せる聞き方にする

- 技術用語には短い補足を添え、違いは使い勝手・配布・運用・変更のしやすさへの影響として説明する。長い比較表や複数の問いを一度に渡さない。
- 答えを受けたら、決まったこととその理由を短く言い換えてから次へ進む。説明が伝わっていない様子なら、次の決定を急がず、その点をかみ砕く。
- ユーザーが迷ったら、観点や具体例を示すか、未決として先へ進む。推奨に引き戻さない。返答がないことを同意と扱わない。
- 提案・推奨と、ユーザーが合意した決定を区別する。合意していないことを決定にしない。要望を勝手に補わず、後から変わった内容は最新の意向に合わせる。

## 技術を提案するとき

- 既存プロジェクトがあれば、判断に関わるコード・設定・依存関係・ドキュメントを見る。既存の構成や標準機能で足りるかを先に調べ、新しい技術が要るなら理由を示す。
- 要件を満たす最も単純な構成を基本に、採用理由を企画書や対話で決まった条件と結びつける。言語・フレームワーク・データベースを一式そろえること自体を目的にしない。
- 対応環境や互換性など、判断に必要な技術的事実は公式情報や既存コードで確かめる。根拠を短く示し、確かめていないことは「未検証」と明記する。

## 二つの文書

会話を知らない実装者が、決まったことと判断の余地を読み取れるように書く。両方に元の企画書への参照を置き、必要な項目だけを簡潔に書く。

- 合意した内容だけを決定事項にする。残したい提案は、未決事項の中で「案」と明記する。
- 推定で埋めない。判断に必要な情報がなければ「未確認」として未決事項に残す。企画書から引き継いだ推定も、合意が取れるまで「推定」のまま未決事項に置く。
- 要件は「何を満たすか」、技術構成は「何を使って実現するか」。重複する説明はもう一方を参照する。

### software-requirements.md

- 目的、利用者、主要な利用の流れ、扱う範囲と今は扱わないこと
- 必要な機能と主要な振る舞い、満たしたかを確かめられる完了条件
- 利用環境やデータの扱いなど、実装に影響する制約
- 要件の未決事項と、実装時に委ねること

### software-stack.md

- 採用する技術と役割、採用理由、選定に関わる制約
- 実装の方向を共有するために必要な構成や外部連携
- 技術の未決事項・未検証事項と、実装時に委ねること

## 保存と報告

- 主要な振る舞いと完了条件、実装の方向を左右する要件と技術選択について認識がそろい、残りを実装時に委ねられる状態になったら、決定事項と委ねることを短くまとめて両文書を保存する。合意済みの内容に再承認を求めない。途中でまとめを求められたら、その時点の内容を保存し、方向を左右する未決が残るなら「検討中」と明記して何が未決かを伝える。
- 保存先は、ユーザーの指定、既存の文書配置、作業ディレクトリの `docs/software-requirements.md` と `docs/software-stack.md` の順に従う。既存ファイルを更新するときは内容を読み、今回の合意に関わる箇所だけを直す。
- 保存前に、企画書と最新の合意に沿っていること、両文書が矛盾しないこと、未決と実装時に委ねることが分かれていることを見直す。
- 保存後は、両文書へのリンクと、残っている未決事項を短く伝える。このスキルの成果物は両文書まで。実装は別途頼まれたときに進める。

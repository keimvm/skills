# RFPから必要最小限の要件と技術構成を決める

渡されたRFPを出発点に、ユーザーと対話しながら、実装を始めるために必要なことを一つずつ決めてください。理解負債がたまらないよう、何を決めるのか、なぜそうするのかを短く説明し、AIからも提案と推奨理由を示します。決まった内容を `software-requirements.md` と `software-stack.md` にまとめ、細かい決定は実装時に委ねます。

## 始め方

- 指定されたRFPを読み、目的・実現したい状態・範囲・制約を短く言い換えて、認識を合わせます。RFPが渡されていない場合や対象が分からない場合は、どのRFPを使うかを尋ねます。
- RFPの未確認・推定・未決事項は、その状態を引き継ぎます。後から変更された内容はユーザーの最新の意向に合わせ、要望を勝手に補いません。
- 既に決まっていることを繰り返し質問せず、実装の方向を左右する未決事項から、今扱う論点を一つ選びます。

## 決める範囲

- 今決めるのは、決めないと実装の方向が分かれること、または後から変えると影響が大きいことです。必要な機能と主要な振る舞い、何ができれば完成か、実現に必要な技術構成を扱います。
- 文書の項目を埋めるためだけの決定は増やしません。将来あるかもしれない要望を理由に、機能・依存関係・構成を追加しません。
- ファイル構成、内部の関数や型、細かな画面配置などは、要件や制約に関わらなければ実装時に委ねます。技術の種類やバージョンも、今選ぶ必要があるものだけ扱います。
- 「未決」と「実装時に委ねること」を分けます。前者はまだ判断が必要な論点、後者は合意した要件・制約の範囲で実装者が決めてよいことです。実装の方向を左右する未決事項を、細部として片付けません。

## 対話の進め方

一回の返答では一つの論点を扱い、次の流れを短く示します。毎回同じ見出しを並べる必要はありません。

1. 今回決めることと、今決める必要がある理由。
2. 選択肢と、それぞれを選んだ場合の違い。比較が必要なときだけ、有力な選択肢を2〜3個示します。
3. AIの推奨と、その理由。どの要望や制約に合うのか、何を諦めるのかも判断に必要な範囲で伝えます。
4. ユーザーの考えを聞く、一つの質問。推奨への賛否だけを求めず、別の考えや疑問も話せる聞き方にします。

- 技術用語には短い補足を添え、違いを使い勝手・配布・運用・変更のしやすさなどへの影響に結びつけて説明します。長い比較表や複数の質問を一度に渡しません。
- 答えを受けたら、決まったこととその理由を短く言い換えてから次へ進みます。説明が伝わっていない様子なら、次の決定を急がず、その点をかみ砕きます。
- ユーザーが迷ったら、観点や具体例を示すか、いったん未決として先へ進みます。推奨に引き戻したり、返答がないことを同意と扱ったりしません。
- AIの提案・推奨と、ユーザーが合意した決定を区別します。合意していない内容は決定事項にしません。

## 技術を提案するとき

- 対象の既存プロジェクトがある場合は、判断に関係するコード・設定・依存関係・ドキュメントを確認します。既存の構成や標準機能で満たせるかを先に調べ、新しい技術が必要なら理由を説明します。
- 要件を満たす最も単純な構成を基本に、採用理由をRFPや対話で決まった条件と結びつけます。言語・フレームワーク・データベースなどを一式選ぶこと自体を目的にしません。
- 対応環境や互換性など、判断に必要な技術的事実は公式情報や既存コードで確認します。根拠を短く示し、確認できていないことや実証が必要なことは未検証と明記します。

## 文書に残す内容

会話を知らない実装者が、決まったことと判断の余地を読み取れるように書きます。両文書に元のRFPへの参照を置き、必要な項目だけを簡潔にまとめます。

- 合意した内容だけを決定事項として記載します。提案を残す必要があれば、未決事項の中で「案」と明記します。
- 項目を埋めるために推定で補いません。判断に必要な情報がなければ「未確認」とし、未決事項に残します。
- 要件は「何を満たすか」、技術構成は「何を使って実現するか」を中心に書き、重複する説明はもう一方の文書を参照します。

### software-requirements.md

- 目的、利用者、主要な利用の流れ、扱う範囲と今は扱わないこと。
- 必要な機能と主要な振る舞い、満たしたかを確かめられる完了条件。
- 利用環境やデータの扱いなど、実装に影響する制約。
- 要件についての未決事項と、実装時に委ねること。

### software-stack.md

- 採用する技術と役割、採用理由、選定に関係する制約。
- 実装の方向を共有するために必要な構成や外部連携。
- 技術についての未決事項・未検証事項と、実装時に委ねること。

## まとめと出力

- 主要な振る舞い・完了条件と、実装の方向を左右する要件・技術選択について認識がそろい、残りを実装時に委ねられる状態になったら、決定事項と委ねることを短くまとめて両文書を保存します。合意済みの内容に再承認を求めたり、不要な質問を続けたりしません。
- 途中でまとめを求められた場合も、その時点の内容を保存します。実装の方向を左右する未決事項が残る場合は「検討中」と明記し、何が未決かを伝えます。
- 保存先の指定や既存の文書配置があれば従います。なければ、作業ディレクトリの `docs/software-requirements.md` と `docs/software-stack.md` に保存します。既存ファイルを更新するときは内容を読み、今回の合意に関係する箇所を更新します。
- 保存前に、RFPと最新の合意内容に沿っていること、両文書に矛盾がないこと、未決事項と実装時に委ねることが区別されていることを確認します。
- 保存後は、両文書へのリンクと、残っている未決事項を短く伝えます。このスキルの成果物は両文書とし、実装は別途依頼されたときに進めます。
